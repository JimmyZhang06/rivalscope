# Agent 7 竞品技术监测 — 现有系统 vs 合同要求差距分析报告

> 依据：《明圣一期-Agent7-竞品监测-内部执行要求-2026-08-01.docx》
> 分析对象：comp-agent 代码库（backend + frontend，截至 agent-v4 分支）
> 分析日期：2026-08-01

---

## 一、合同要求概览

Agent 7 的合同任务是**在冻结范围内完成一个可验证的基础闭环**：

| 维度 | 要求 |
|------|------|
| 固定范围 | 5 家竞品、10 个批准公开来源、不高于每周 1 次、10 条监测记录、5 份竞品画像 |
| 交付物 | A7-01~A7-08（竞品名单、来源配置、来源存证、监测记录、画像、横向对比、变化提醒、运行日志） |
| 验收门槛 | 来源存证 10/10、结构化处理 ≥9/10、事实准确率 ≥90%、画像 5/5、零容忍 0 起 |
| 不做承诺 | 全网覆盖、竞品非公开信息、深度技术研判、绕过访问控制、正式优劣/侵权判断 |

## 二、现有系统能力盘点

### 已具备的能力

| 能力 | 对应模块 | 说明 |
|------|---------|------|
| 多租户组织 | `User.org_id` + `Organization` | 一人一企，企业维度共享 |
| 用户认证与角色 | JWT + `role` (user/admin) | 基础 RBAC |
| 调研任务 CRUD | `ResearchTask` + `/api/research` | 创建、列表、详情、删除 |
| 来源分级 | `Source.tier` (official/media/community/other) | 启发式域名分级 |

| 定时追踪 | `Tracker` + scheduler | 支持 daily/weekly/monthly，进程内 60s 扫描 |
| 运行日志 | `TaskStep` | 每步记录 phase/title/detail |
| 变化摘要 | `ResearchTask.change_summary` | 与上一期对比的变更 markdown |
| 报告生成 | `agent.py` 编排流水线 | planning → searching → analyzing → reporting |
| 通知推送 | `Notification` + email/webhook | 站内通知 + SMTP + 企业微信/钉钉/飞书 |
| 配额管理 | `month_usage()` + `check_quota_or_403()` | 企业共享配额 + 成员个人子额度 |
| 计费与订单 | `Order` + `/api/billing` | 模拟支付，套餐升级 |
| 管理后台 | `/api/admin/*` | 平台统计、用户管理、企业管理 |
| 个人中心 | `AccountPage` | 用量统计、登录历史、订单记录 |
| AI 助手 | `/api/assistant` | 跨报告问答，多会话管理 |
| 产业链图谱 | `GraphProject` | 独立的图谱构建模块 |

```
research_tasks → task_steps (执行步骤日志)
```

## 三、逐项差距分析

### A7-01：竞品名单维护

| 合同要求 | 现有系统 | 差距 |
|----------|---------|------|
| 5 家竞品，含别名、官网、技术主题、监测关键词 | `ResearchTask.competitors` 是逗号分隔的纯文本，无独立竞品实体 | **缺失独立竞品模型**，别名/官网/技术主题/关键词无法结构化存储和管理 |
| 竞品列表可维护、可审计 | 无竞品 CRUD 接口 | **缺失竞品管理 API 和前端页面** |

### A7-02：批准来源配置

| 合同要求 | 现有系统 | 差距 |
|----------|---------|------|
| 10 个来源，含名称、URL/入口、来源层级、访问方式、备选/状态 | `Source` 模型有 `url`、`tier`、`domain`，但无"批准来源"概念，无备选/状态字段 | **来源是任务产出物而非配置项**，缺少来源注册、审批、状态管理流程 |
| 来源可配置、可审计 | 无来源管理界面 | **缺失来源管理 API 和前端** |

### A7-03：来源存证（**最关键的缺口**）

| 合同要求 | 现有系统 | 差距 |
|----------|---------|------|
| 10/10 记录：URL/文件、页面快照、发布时间或无日期状态、采集时间、原文证据 | `Source` 有 `url`、`published_at`、`raw_content`、`domain`、`tier`，但**无页面快照（截图/HTML 存档）**，无采集时间独立字段（只有 `TaskStep.created_at`） | **缺页面快照能力**。合同要求"页面快照"——截图或 HTML 存档，当前系统只存了原文摘录（截断 8000 字），未存完整页面 |
| 证据链完整可追溯 | `raw_content` 截断到 8000 字符，非完整原文 | **原文截断**，不满足"原文证据"要求 |

### A7-04：监测记录

| 合同要求 | 现有系统 | 差距 |
|----------|---------|------|
| 10 条监测记录：结构化提取、去重/关联、新鲜度、置信度、冲突/待核实状态 | `ResearchTask` 有状态流转，`Source` 有 `tier` 和 `published_at` | **缺置信度字段**（`Source` 无 confidence），**缺冲突/待核实状态标记**，**缺去重/版本关联机制** |
| 结构化字段提取 | `report_data` 是 JSON 字符串，包含 SWOT/评分/竞品对比 | 部分满足，但字段不固定、不可配置 |
| 无来源或冲突不输出确定性结论 | 无此逻辑约束 | **缺判断置信度门槛** |

### A7-05：竞品画像

| 合同要求 | 现有系统 | 差距 |
|----------|---------|------|
| 5 份画像，按冻结固定维度模板，附来源与更新时间 | 无竞品画像功能 | **完全缺失**。当前只有通用的 `report_markdown` + `report_data`，无固定维度的竞品画像模板 |
| 固定维度模板 | 无模板配置 | **缺画像模板定义和管理** |

### A7-06：横向对比与摘要

| 合同要求 | 现有系统 | 差距 |
|----------|---------|------|
| 1 套固定维度对比草稿、摘要、来源说明 | `report_data` 中有 `competitors` 评分，有 `verdict` 摘要 | **部分满足**。有竞品对比和摘要，但非"固定维度"模板化输出，缺少正式的横向对比报告 |
| 按冻结维度对比 | 维度由 LLM 自由生成，不可配置 | **缺固定维度模板** |

### A7-07：变化提醒与 CRM 任务

| 合同要求 | 现有系统 | 差距 |
|----------|---------|------|
| 按冻结规则提醒：变化内容、来源、负责人、提醒状态和任务记录 | `Tracker` 有 `change_summary`，`Notification` 有通知，`push_email`/`push_webhook` 已实现 | **部分满足**。有定时追踪和通知，但缺"变化定义规则"配置（什么程度算变化），缺 CRM 任务管理 |
| 提醒渠道可配置 | 有 email/webhook | 基本满足 |

### A7-08：运行日志

| 合同要求 | 现有系统 | 差距 |
|----------|---------|------|
| 全量运行日志：运行时间、来源访问、结果、错误、最后成功时间、成本 | `TaskStep` 有步骤日志，`Task.status`/`error` 有状态 | **缺成本记录**（LLM token 消耗、搜索 API 费用），**缺来源访问结果日志**（成功/失败/重试） |
| 模型调用记录：模型、状态、可得 Token 与成本 | 无模型调用记录 | **完全缺失** |
| 统一日志和审计 | 无审计日志表 | **完全缺失** |

### 共用平台交付

| 合同要求 | 现有系统 | 差距 |
|----------|---------|------|
| 容器镜像或可执行程序 | 无 Docker 配置 | **缺失** |
| 部署清单、数据库迁移工具 | 无迁移工具（仅 SQLite 自动建表） | **缺失** |
| 配置模板、环境变量说明 | `config.py` 有 env 变量，但无模板 | 部分满足 |
| 部署/备份/恢复/迁移说明 | 无 | **缺失** |
| 管理员及业务用户手册 | 无 | **缺失** |
| 自测结果、UAT 结果、试运行报告 | 无 | **缺失**（需在验收前完成） |
| 成本报告 | 无 | **缺失** |
| 数据导出文件及字段说明 | 无导出功能 | **缺失** |
| 统一日志和审计 | 无审计日志 | **缺失** |

### 安全与权限（合同第五章）

| 合同要求 | 现有系统 | 差距 |
|----------|---------|------|
| 普通用户不得修改品牌红线、监测来源、匹配规则、预算或密钥 | 基础 RBAC（user/admin），**无角色细粒度控制** | **缺细粒度 RBAC**。需要：业务 Owner、来源管理员、分析员、事实复核人、技术负责人、QA/UAT、人工接管负责人等角色 |
| 密钥不得出现在代码仓库、前端或普通日志 | SMTP 凭据已清除（v4 修复），但**无密钥管理系统** | 部分满足 |
| 预算达到 80% 告警、100% 暂停 | 有配额检查（100% 拒绝），**无 80% 预警** | **缺预算预警机制** |
| 第三方来源失败保留任务、错误、最后成功时间 | Tracker 有 `last_run_at`，但**不记录失败详情和最后成功时间** | **缺失败记录** |
| "暂停—留证—通知—减损—复盘—恢复"事件处理 | 无事件处理流程 | **缺失** |
| 两级冻结 + 执行快照 | 无版本快照机制 | **缺失** |

### 阶段与验收流程（合同第九章）

| 合同要求 | 现有系统 | 差距 |
|----------|---------|------|
| 阶段 0 冻结基线 | 无冻结机制 | **缺失** |
| 每次提验锁定候选版本、构建哈希、模型/参数 | 无版本管理 | **缺失** |
| 同一结论只使用同一执行快照 | 无快照机制 | **缺失** |
| 备选来源机制 | 无 | **缺失** |
| P0/P1 阻断验收、P2 遗留清单、P3 需求池 | 无缺陷管理系统 | **缺失** |
| 复测覆盖原失败编号 + 回归项 | 无 | **缺失** |

## 五、改造方案

### 第一批：P0 — 阻断阶段 2B 验收的核心能力（建议 2-3 周）

#### 1. 竞品实体模型（G1/G3）

**新增 `Competitor` 模型**：

```
competitors
  id, org_id, name, alias, website, tech_focus,
  keywords (JSON), status (active/paused/archived),
  created_at, updated_at
```

- 5 家竞品的结构化注册与管理
- 别名、官网、技术主题、监测关键词独立字段
- 企业维度隔离（`org_id`）
- 前端：竞品管理页面（CRUD + 关键词管理）

#### 2. 来源存证增强（G1/G2）

**新增 `SourceArchive` 模型 + 改造 `Source`**：

```
source_archives
  id, task_id, source_id,
  snapshot_html (TEXT),           -- 完整 HTML 存档
  snapshot_text (TEXT),           -- 纯文本提取
  snapshot_format (enum),         -- html/text/pdf/image
  published_at,                   -- 来源发布时间（保留原字段）
  collected_at,                   -- 采集时间（独立字段）
  access_status,                  -- success/failed/timeout/blocked
  access_error,                   -- 失败原因
  raw_content_full (TEXT),        -- 完整原文（不截断）
```

- 调研执行时自动抓取页面 HTML 存档
- 区分 `published_at`（来源发布时间）和 `collected_at`（采集时间）
- 记录访问状态（成功/失败/超时/被拦截）
- `Source.raw_content` 从 8000 字符截断改为存储完整文本

#### 3. 结构化字段与置信度（G4）

**改造 `Source` 模型**：

```
sources
  + confidence (float 0-1)       -- 置信度
  + conflict_status (enum)        -- none/conflict/pending_verify
  + conflict_note (TEXT)          -- 冲突说明
  + dedup_group (str)             -- 去重组标识
  + version_of (int)              -- 指向被关联的来源 ID（版本演变）
  + is_duplicate (bool)           -- 是否为重复转载
```

- 提取时自动标记置信度（LLM 自评 + 来源层级加权）
- 冲突检测：同一事实多来源不一致时标记 `conflict`
- 去重：URL 哈希 + 内容指纹，标记转载关系
- "无来源不输出确定性结论"——报告生成时校验

#### 4. 竞品画像（G5/G6）

**新增 `CompetitorProfile` 模型 + 模板系统**：

```
competitor_profiles
  id, org_id, competitor_id, template_id,
  profile_data (JSON),            -- 按模板维度填充的结构化数据
  data_snapshot (JSON),           -- 冻结时数据快照
  sources (JSON),                 -- 引用来源 ID 列表
  created_at, updated_at,         -- 更新时间
  frozen_at,                      -- 冻结时间（阶段 0 后不可改）
  status (draft/reviewed/frozen)
```

**画像模板**（冻结配置）：

```
profiles_templates
  id, org_id, name,
  dimensions (JSON),              -- 固定维度定义 [{
    key, label, weight, fields: [{key, label, type}]
  }],
  version,                        -- 模板版本
  frozen_at,                      -- 冻结时间
  created_by, created_at
```

- 画像按冻结模板的固定维度生成
- 模板版本化管理，冻结后不可修改
- 每条画像附来源链接和更新时间

#### 5. 细粒度 RBAC（G7）

**改造权限系统**：

```
roles:
  - system_admin     -- 系统管理员（原有 admin）
  - business_owner   -- 业务 Owner（确认竞品/范围/规则）
  - source_admin     -- 来源管理员（维护 10 个来源）
  - analyst          -- 竞争情报分析员（字段抽取/画像/对比）
  - fact_checker     -- 事实复核人（核对关键事实）
  - tech_lead        -- 技术负责人（调度/存证/日志）
  - qa               -- QA/UAT
  - human_override   -- 人工接管负责人

permissions:
  - competitor:create,read,update,delete,freeze
  - source:register,approve,update,freeze
  - profile:generate,review,freeze
  - report:generate,publish,override
  - tracker:create,update,delete,run
  - budget:view,configure,approve_override
  - key:view,rotate
  - audit:read
  - system:configure
```

- 后端：`Permission` 模型 + `user_id × permission` 关联 + 装饰器/依赖检查
- 前端：按角色隐藏/禁用操作按钮
- 合同要求"普通用户不得修改品牌红线、监测来源、匹配规则、预算或密钥"→ 对应权限实现

#### 6. 横向对比报告模板化（G6/G16）

- 在 `profiles_templates` 中增加"横向对比模板"
- 固定维度（如：产品参数、技术路线、认证标准、价格区间、市场定位）
- 对比结果输出为结构化 JSON + Markdown
- 前端：对比报告查看页面

### 第二批：P1 — 安全、审计与流程保障（建议 1-2 周）

#### 7. 审计日志系统（G8/G9）

**新增 `AuditLog` 模型**：

```
audit_logs
  id, user_id, org_id, action, resource_type, resource_id,
  input (JSON), result (JSON), status, error,
  model_name, tokens_used, cost,
  ip, user_agent, created_at
```

- 所有关键操作记录：时间、操作者、输入、结果、状态
- 模型调用记录：模型名、token 消耗、费用
- 来源访问记录：成功/失败/错误详情
- 预算消耗累计 + 80% 预警

#### 8. 预算预警（G11）

- `check_quota_or_403` 增加 80% 阈值通知
- 调度器在每次运行前检查预算状态
- 达到 100% 自动暂停批量任务

#### 9. 执行快照与版本锁定（G14）

**新增 `ExecutionSnapshot` 模型**：

```
execution_snapshots
  id, org_id, tracker_id, run_id,
  config_hash,                   -- 配置哈希（竞品/来源/规则/参数）
  model_params (JSON),           -- 使用的模型和参数
  kb_version,                    -- 知识库/规则版本
  deployment_env,                -- 部署环境标识
  candidate_version,             -- 候选版本号
  build_hash,                    -- 构建哈希
  created_at, created_by
```

## 七、现有系统优势

虽然差距较大，但现有系统已具备一些**合同不要求但非常有价值**的基础能力：

1. **定时追踪调度器**（scheduler.py）— 合同要求"不高于每周 1 次"，现有系统支持 daily/weekly/monthly，超过合同要求
2. **多源通知**（email + webhook）— 覆盖企业微信/钉钉/飞书
3. **企业级配额管理** — 企业共享配额 + 成员子额度
4. **来源分级**（tier）— 官方/媒体/社区/其他四层分级
5. **AI 助手** — 跨报告问答能力（合同未要求，可增强用户体验）
6. **完整的前端工作台** — 任务管理、追踪管理、个人中心、管理后台

这些能力可以作为 Agent 7 的**差异化优势**，在交付中明确标注为超出合同范围的增值功能。

## 八、风险提示

1. **页面快照是最大技术风险** — 需要集成 Playwright/Puppeteer 或第三方截图服务（如 screenshotapi.net），对部署环境有额外要求
2. **原文截断问题** — 当前 `RAW_CONTENT_LIMIT = 8000` 需要评估是改为不截断（数据库压力）还是改为可配置阈值
3. **RBAC 改造范围大** — 影响所有 API 端点和前端页面，需要全面回归测试
4. **模板冻结机制** — 需要在"灵活性"和"冻结后不可改"之间平衡，建议用版本号 + 软删除实现
5. **成本追踪精度** — 需要精确记录每次 LLM 调用的 token 消耗，取决于 LLM SDK 的返回值
