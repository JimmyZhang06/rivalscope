# 前端导航与首页重构实施计划

## 1. 目标

将当前以“调研、追踪、画像、图谱”模块为中心的控制台，渐进重构为以“事件、对象、资产、监测、分析行动”为中心的聚合情报平台。

本轮仅调整前端信息架构、应用框架和首页体验：保留所有旧路由与后端契约，不删除现有功能，不引入数据库迁移。

## 2. 当前问题

1. `AppLayout.tsx` 暴露六个分组和十多个一级入口，用户必须先理解内部模块。
2. “情报资产”属于平台级能力，却被归入“调研”；“竞品管理”被归入“追踪”，概念关系不清。
3. 画像模板、画像任务、横向对比等二级能力占据一级导航。
4. 产品品牌仍为“竞品调研 Agent”，与聚合情报平台定位冲突。
5. 首页围绕报告、画像数量和任务状态饼图，不能优先回答“发生了什么、什么需要处理”。
6. 首页客户端分别拉取调研、画像、追踪、通知，并每 30 秒整体刷新；请求重复且静态数据也被轮询。
7. 固定 `w-56` 侧栏缺少移动端抽屉、折叠和统一顶栏；通知和用户操作位置分散。

## 3. 目标导航

一级导航控制在七个核心入口：

| 一级入口 | 现有路由 | 说明 |
|---|---|---|
| 情报总览 | `/app` | 事件优先首页 |
| 情报事件 | `/app/intelligence` | 最新变化、异常和处理入口 |
| 关注对象 | `/app/competitors` | 本轮仅更名，后续升级为统一对象中心 |
| 情报资产 | `/app/assets` | 报告、画像、图谱等统一目录 |
| 监测中心 | `/app/trackers` | 规则和运行状态 |
| 分析工作台 | 前端分组 | 包含专题调研、画像与对比、关系图谱 |
| AI 助手 | `/app/assistant` | 平台级辅助入口 |

“套餐与用量、账号、企业、管理后台、审计日志”移动到侧栏底部或用户菜单，不与核心工作流竞争。

所有现有 URL 保持可用。`/app/new`、`/app/tasks`、`/app/profiles/*`、`/app/graph` 继续使用，只改变菜单层级和显示名称。

## 4. 应用框架改造

### 4.1 左侧导航

- 品牌改为“竞争情报平台”或“情报聚合平台”。
- 平台入口与分析工具分组，减少视觉噪声。
- 支持桌面折叠和移动端抽屉。
- 活跃项同时具备颜色和左侧标记，不仅依赖整块高饱和背景。
- 分析工作台允许折叠，默认保留用户当前展开状态。

### 4.2 顶栏

新增统一顶栏，容纳：

- 当前页面标题或面包屑。
- 全局快捷创建菜单。
- 通知入口。
- 用户菜单和移动端导航按钮。

快捷创建菜单包含：添加关注对象、创建监测、发起专题调研、生成画像、构建图谱。

本轮不实现虚假的工作区切换和全局搜索；可保留视觉/组件接口，但没有真实数据契约时不得展示不可用控件。

## 5. 首页目标结构

首页从“库存统计看板”改为“事件和行动总览”。

### 第一屏

1. 页面标题：`情报总览`。
2. 摘要文案：展示新事件、运行中事项、失败事项数量。
3. 三个主要操作：添加对象、创建监测、发起分析。
4. 四张行动指标卡：事件总量、正在运行、已完成、需要关注。

指标优先复用 `getIntelligenceEventSummary()`，点击后进入带对应筛选语义的事件页面；若现有事件页尚不读取 URL 查询参数，本轮可以只跳转到页面，不伪造过滤结果。

### 核心区域

- 左侧：最新情报事件，复用 `listIntelligenceEvents()`，展示类型、状态、摘要、时间和详情入口。
- 右侧：需要处理，聚合失败事件、运行中事件和未读通知；每项必须有明确去向。

### 第二屏

- 最近情报资产：复用 `listAssets()`，最多展示 5 项。
- 活跃监测：继续复用 `listTrackers()`，仅在有权限和数据时展示。
- 快速分析：专题调研、画像与对比、关系图谱三个入口。

删除首页任务状态饼图和大面积画像库存展示；这些信息留在专业页面。

## 6. 数据请求策略

1. 首屏关键请求：事件摘要、事件列表、资产列表并行执行。
2. 监测和未读通知作为非关键请求，失败时局部降级，不阻断首页。
3. 只有存在运行中事件时才每 15 秒轻量刷新事件和摘要。
4. 资产与监测不跟随事件轮询；用户手动刷新或重新进入页面时更新。
5. 删除重复的未读通知请求。
6. 区分整页失败与局部失败；局部模块显示重试，不伪装为空数据。

## 7. 组件边界

优先抽取但不过度设计：

- `navigation.ts`：导航配置和类型。
- `Sidebar.tsx`：桌面/移动导航。
- `Topbar.tsx`：页面级操作区。
- `CreateMenu.tsx`：统一快捷创建菜单。
- `DashboardMetricCard.tsx`。
- `DashboardEventFeed.tsx`。
- `DashboardAssetList.tsx`。
- `DashboardActionPanel.tsx`。

如果抽取会导致当前小组件在单个页面外没有复用价值，可保留为 `DashboardPage.tsx` 内部组件，避免为了目录结构制造复杂度。

## 8. 响应式与可访问性

- `< 1024px` 使用抽屉侧栏，页面不保留固定左边距。
- 键盘可打开/关闭创建菜单和移动侧栏；Escape 可关闭浮层。
- 所有图标按钮提供 `aria-label`，菜单具备正确角色和焦点顺序。
- 状态不能只依赖颜色，必须同时显示文字或图标。
- 尊重 `prefers-reduced-motion`，避免不必要的位移动画。

## 9. 文件范围

预计修改：

- `frontend/src/layouts/AppLayout.tsx`
- `frontend/src/pages/app/DashboardPage.tsx`
- 必要时新增 `frontend/src/components/layout/*`
- 必要时新增 `frontend/src/components/dashboard/*`
- 必要时少量修改 `frontend/src/api/client.ts` / `frontend/src/api/types.ts`

禁止修改后端、数据库模型、API 行为和现有路由路径。不要删除旧页面。

## 10. 验收门禁

1. 侧栏核心入口不超过七个，分析能力以二级层级呈现。
2. 桌面、平板和手机宽度下均可访问全部导航与用户操作。
3. 首页首屏以事件和待处理事项为主，不再以画像/报告库存为主。
4. 关键模块具有 loading、empty、error、partial error 状态。
5. 旧深链接全部保持可用。
6. `npm run build` 通过，`npm audit` 无高危漏洞。
7. 不纳入 `dist`、本地数据库、调试脚本或用户未跟踪文档。
8. 提交前执行 `git diff --check`，并报告改动文件、构建结果和已知限制。

## 11. 实施顺序

1. 冻结导航配置和名称。
2. 拆分并重构 AppShell/Sidebar/Topbar，完成响应式布局。
3. 重写首页数据加载与区块结构。
4. 复用事件/资产类型和 API，修复局部错误处理。
5. 完成移动端、键盘和空状态检查。
6. 运行构建与审查，形成单一意图提交。
